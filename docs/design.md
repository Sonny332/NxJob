# NxJob Design Guide

## Source Reference

This guide adapts the PlayStation-inspired design reference generated by:

```powershell
npx getdesign@latest add playstation
```

NxJob should not copy PlayStation branding. Use the reference as a visual system cue: quiet chrome, sharp contrast, restrained blue accents, pill actions, 8px cards, and flat surfaces.

## Product Tone

NxJob is a compact browser-extension utility for repeated job application work.

The UI should feel:

- Calm and work-focused.
- Fast to scan.
- Low-friction and low-decoration.
- Premium but not flashy.
- Action-oriented without hiding risk.

The UI should not feel:

- Like a marketing landing page.
- Like a game console page.
- Like a dashboard overloaded with cards.
- Like an AI chat product.
- Like an automation bot that acts without user control.

## Design Principles

- Use a three-surface system: light canvas, dark header/status surface, and blue action accent.
- Keep chrome quiet. Let state, evidence, and user actions carry the interface.
- Use blue sparingly for primary actions and selected states.
- Use flat surfaces. No decorative gradients, orbs, bokeh, glassmorphism, or resting drop shadows.
- Use 8px cards for grouped evidence or results.
- Use full pill buttons only for primary actions.
- Use small-radius fields and evidence rows.
- Keep all text compact and scannable.
- Every AI or rule-based recommendation must show evidence, confidence, or source.
- All high-impact actions stay user-confirmed.


NxJob semantic additions:

```text
success: #1f7a4d
success-soft: #e8f5ee
warning: #c81b3a
warning-soft: #fbe8ed
attention: #b56a00
attention-soft: #fff3df
unknown: #6b6b6b

```

Usage:

- `primary` is for primary buttons, active capture state, and important links.
- `success` is for confirmed good signals, such as `supports` or successful capture.
- `warning` is for explicit blocking risk, such as `does_not_support`.
- `attention` is for uncertain but actionable risk, such as `likely_not_supports` or `needs_confirmation`.
- `unknown` is for no evidence or offline/neutral states.
- Do not use orange/red for normal CTAs.

## Typography

Use system UI fonts, not PlayStation SST.

```text
font-family: Inter, ui-sans-serif, system-ui, -apple-system, BlinkMacSystemFont, "Segoe UI", sans-serif
```

Popup scale:

```text
title: 20px / 700 / 1.2
section-title: 13px / 700 / 1.3
body: 13px / 400 / 1.45
caption: 12px / 400 / 1.4
button: 13px / 700 / 1.2
badge: 11px / 600 / 1.2
```

Rules:

- No viewport-scaled font sizes.
- No negative letter spacing.
- Avoid oversized headings in the plugin popup.
- Use strong labels for scanning, not decorative display type.

## Shape and Spacing

Shape:

```text
radius-none: 0px
radius-sm: 4px
radius-md: 8px
radius-lg: 16px
radius-full: 9999px
```

Spacing:

```text
xxs: 4px
xs: 8px
sm: 12px
md: 16px
lg: 24px
```

Rules:

- Popup outer padding: 16px.
- Section gap: 12-16px.
- Evidence row padding: 8-12px.
- Result card padding: 12px.
- Minimum click target: 38px in compact popup, 44px where space allows.
- Cards use 8px radius.
- Text inputs use 4px radius.
- Primary actions use full pill only when visually appropriate; compact stacked popup buttons may use 6-8px radius for readability.

## Layout

MVP popup width:

```text
min-width: 320px
preferred-width: 360px
max practical popup height: 560px
```

Popup structure:

```text
Header
  NxJob title
  local service status badge

Current page
  title
  url
  selected text length
  page text excerpt length

Actions
  Analyze Sponsorship
  Tailor Resume
  Fill Form Answer

Latest result
  JobLead id
  duplicate status
  next-step note

Message / error
```

Rules:

- Keep the popup single-column.
- Do not nest cards inside cards.
- Do not add a marketing hero.
- Do not add decorative imagery.
- Prefer one primary action group over separate large sections.
- Long URLs and IDs must wrap safely.

## Components

### Service Status Badge

Purpose: show whether local service is reachable.

States:

```text
checking: unknown text on unknown-soft
online: success text on success-soft
offline: warning text on warning-soft
```

Rules:

- Status badge sits in the header.
- Offline must be visible before the user clicks an action.
- Offline message should say what to do: start local service, then retry.

### Action Button

Primary actions:

```text
Analyze Sponsorship
Tailor Resume
Fill Form Answer
```

Rules:

- Buttons are stacked in popup MVP.
- Button labels are exact and stable.
- Disabled/loading state says `Capturing...` for the current action.
- Do not auto-run workflow on page load.
- Do not auto-submit forms.

### Current Page Panel

Shows:

- Page title.
- URL.
- Selected text length.
- Page excerpt length.

Rules:

- Selected text is preferred over full page text.
- If selected text is empty, still show page excerpt length.
- Keep this panel factual; do not infer fit or sponsorship here.

### Capture Result

Shows:

- `JobLead` id.
- New vs duplicate.
- Existing duplicate id when available.
- Short next-step message.

Rules:

- Success result uses `success`.
- Duplicate result uses `attention`, not error.
- Never hide the id; it is useful for debugging.

### Sponsorship Result

M4 should use this component.

Statuses:

```text
supports: success
does_not_support: warning
likely_supports: success with "likely" label
likely_not_supports: attention
needs_confirmation: attention
unknown: unknown
```

Required display:

- Status label.
- Confidence when available.
- Evidence source.
- Evidence excerpt.
- Questions to confirm.
- Caveat: not a legal conclusion.

Rules:

- `likely_*` must never look as final as explicit `supports` or `does_not_support`.
- AI inference must be visually marked as inference.
- Evidence rows use 8px cards or flat rows with hairline dividers.

### Error Message

Rules:

- Use plain text.
- Explain recovery action.
- Keep technical details short.
- Never blame the user.

## Interaction Rules

- User must click to capture.
- User must review before form filling.
- User must submit applications manually.
- AI output must come back through local record storage before being shown as a decision aid.
- Do not use hidden background scraping.
- Do not show confidence without evidence.
- If a workflow is unavailable, show the next milestone message rather than a fake result.

## M4 UI Requirements

When implementing `Analyze Sponsorship v1`, update popup UI to show:

- Capture first if no `JobLead` exists.
- Sponsorship status card.
- Evidence list.
- Confidence and source.
- `needs_confirmation` questions.
- Local-rule vs AI-fallback indicator.
- Legal caveat: `Not a legal conclusion`.

M4 must keep the current M3 capture behavior intact.

## Do and Don't

Do:

- Use `#0070d1` only for primary actions and active states.
- Use flat cards with 8px radius.
- Use compact, repeated utility components.
- Show source/evidence for every recommendation.
- Keep offline and error states obvious.
- Keep UI copy literal and action-focused.

Don't:

- Do not add hero sections, decorative backgrounds, or large illustrations.
- Do not use gradients except if explicitly added later for a single branded banner.
- Do not use shadows on resting cards.
- Do not use orange/red for normal actions.
- Do not make every surface blue.
- Do not bury risk warnings below the fold.
- Do not expose development scripts to non-technical users in user-facing UI.

## Design Review Checklist

Before merging UI work:

- The UI still fits at 320px width.
- Buttons and labels do not wrap awkwardly.
- URLs and IDs wrap safely.
- Offline state is visible.
- Error state includes recovery action.
- Every AI/rule output shows evidence or source.
- No automatic submit behavior was introduced.
- No decorative gradient/orb/shadow was introduced.
- Color semantics match this file.
